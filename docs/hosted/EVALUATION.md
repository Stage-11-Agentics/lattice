# Lattice Hosted: Evaluation Contract

What "done" means for Lattice v2's hosted mode, and exactly how it is verified. Criteria IDs (AC-n) come from `sequence/USER_STORIES.md`; mechanics come from `SPEC.md`; guardrails (G-n) from `SPEC.md` §14; tickets (H-n) from `BUILDPLAN.md`.

Verifiability tags:

- `autonomous`: a build agent proves it alone, with a named command.
- `operator-assisted`: needs something only the operator can supply, named with its deadline.
- `external-oracle`: needs a real artifact outside the repository to judge against.
- `felt`: a human drives it; no test settles it. Scheduled as a checkpoint in §4.

## 1. Harness

| Name | Command | When |
|---|---|---|
| **Project gate** | `uv run ruff check src/ tests/ && uv run ruff format --check src/ tests/ && uv run pytest -q` | Every PR, at its final head. Green CI at that exact head (lint, type-check, test on 3.12, 3.13, and 3.14) satisfies it, and the Merge Captain does not rerun it locally; locally the captain runs only what CI cannot, the per-PR torture lane and perf where required. The landing receipt records CI's default-suite wall time |
| Parity | `uv run pytest tests/parity -q` | Inside the gate; named separately for evidence |
| Torture, per PR | `uv run pytest -m "torture and not envelope" -q` | Every PR touching `ops/`, `storage/`, `server/`, or `remote/` once any torture test exists (an empty selection, pytest exit code 5, passes before then), run locally by the Merge Captain at the exact head |
| Envelope | `uv run pytest -m envelope -q` | Background only; never a gate. After every landing that touches `ops/`, `storage/`, `server/`, or `remote/`, the Merge Captain runs it against the newest `v2` head (runs coalesce). It never holds the landing slot or pauses admission: a failure files a ticket against the landing that introduced it, and landings continue. The ticket that owns an envelope test (H-10b, H-15, H-13b) runs it while building and reports the result in its PR |
| Torture, complete | `uv run pytest -m torture -q` | After H-15, and before CP3, CP4, and the release gate |
| Scenario rehearsal | `uv run pytest -m torture tests/torture/test_scenarios.py -q` | Before CP3, CP4, and the release gate (CP1 and CP2 rely on the tests their tickets own, including H-11's two-worktree mini rehearsal in the default suite) |
| Perf | `uv run pytest -m perf tests -q` | On the operator's laptop (the G-9 reference machine): at H-6, and before CP3, CP4, and the release gate. H-0 records the baseline from the pre-refactor code |
| Docs agent test | Procedure in §3, AC-44 | H-17 and terminal validation |

- The `envelope` marker marks the envelope-scale torture tests: AC-7's sync envelope, AC-47's supported-size case, and AC-42's load tests. Every envelope test also carries `torture`, so the complete torture suite includes them. They take minutes, so the per-PR torture lane leaves them out and the Envelope lane runs them.
- The default suite excludes the `torture` and `perf` markers (`addopts = "-m 'not torture and not perf'"`), runs in parallel after H-19 (`-n auto`), and must stay hermetic: servers bind `127.0.0.1:0` in-process, every board lives under `tmp_path`, nothing reads the operator's `~/.config` (tests set `XDG_CONFIG_HOME` and `XDG_DATA_HOME` to temp dirs). A test that reaches a stopped or restarting server sets the remote's `retry_seconds` to what the test needs (at most 1 s unless the test is about retries), so the 15-second default never stalls the suite.
- **Speed budget (G-9):** after H-19, the default suite runs in 40 seconds or less on the operator's laptop. When it nears the budget, prune redundant or excessive tests rather than raising the budget; the gate is not moved to Atlas to meet it. No new default-suite test file may exceed 5 seconds. Each landing receipt records the default-suite wall time from CI.
- **Local latency (perf):** on a generated 1,000-task board with long logs and 300 archived tasks, the median of 5 runs of `show`, `list`, `status`, and `create` stays within 15% or 20 ms of the v1 baseline, whichever is larger, and `create` within 100 ms of it (`SPEC.md` §5). Timing checks never run in the default suite or in CI, where machines differ.
- CI must run on pull requests to `v2` (H-0 adds `v2` to `.github/workflows/ci.yml` triggers).

## 5. Release gate

`v2` merges to `main` only when all of these hold, and only with the operator's named approval:

1. Project gate green at the `v2` head, torture green at the same head, and the perf check green on the operator's laptop.
2. Parity (local and hosted) green.
3. Terminal validation report green (lattice-orchestrator-v2 Phase 2), or residuals named and accepted by the operator.
4. CP1 to CP4 passed.
5. **Trial, about one week:**
   - *Local:* the operator's own Lattice install (the editable checkout every agent on the laptop runs) switched to `v2`, across all local boards. Rollback is code-only: `git switch` of that install to the prior commit restores v1's code, but a board v2 has written is not guaranteed to work under v1 (for example, erased tasks reappear; SPEC §15).
   - *Hosted:* two or three projects of the operator's choosing on the production host. Every trial client, box images included, installs Lattice from the `v2` branch, never from PyPI. The guide's move-back steps have been rehearsed once before the trial starts (AC-44), so a hosted board can return to local.
   - Every day: `lattice server project doctor <slug>` clean for every hosted trial board (it runs under the project's work lock, so it never races a write); `lattice doctor` clean on every local trial board; `lattice remote verify` clean on every trial client that wrote, which proves no acknowledged write was lost; no parity regression; no duplicate short ID. The operator makes the call when it is working well.

`main` then goes to `prod` and PyPI as separate steps, each with the operator's named approval. Merging is not releasing: no ticket in this build publishes a package.
